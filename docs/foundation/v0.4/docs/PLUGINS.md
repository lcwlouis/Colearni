# Teaching plugins and reusable artifacts

## One host contract, multiple implementations

The first-party application uses reviewed native renderers and interactive plugins. The same logical contract specifies identity, exact version, validated input/state, semantic targets, meaningful events, source/assumption information, fallback and requested capabilities. This is not a build-system plugin or browser extension.

Native structured cards and optional MCP Apps are two adapter paths, not two competing ownership models. See MCP_APPS.md for the proposed interoperability layer.

## Initial reviewed tools

**Worked example:** ordered steps with stable targets, optional explanations and explicit source/tutor origin. Reveal controls do not imply a required quiz after every step.

**Affine-function explorer:** developer-authored y = a*x + b with numeric ranges, labels, reset and a table/text alternative. Use x ∈ [-5,5], a ∈ [-3,3], b ∈ [-5,5] in the synthetic fixture. Verify a=2,b=1,x=3 produces 7; a=0 makes output constant. No arbitrary expression evaluation or generated JavaScript. This is not an orbital-physics engine.

The MCP spike exposes the same explorer through a permitted HTML app. Do not expand to a universal simulator as part of the interoperability test.

## Future generation and review

Private experiment → explicit submission → separate reviews → versioned approved release → discovery. Generation does not install code automatically. Review attaches to immutable code/assets/dependencies and requested permissions; a new release is a new decision. A source licence and runtime permissions are separate questions.

Review dimensions: isolation/tool access, supply-chain/package integrity, mathematical/domain correctness, valid ranges/units, accessibility, interaction consistency, resource use, privacy and export safety. A successful render or an AI-generated test is not independent verification.

Published package contains the reusable engine and permitted examples, not private papers, notebook content, conversations or keys. A publication report identifies included/excluded material. Licence compatibility is checked before redistribution.

## Discovery and autonomy

Agents may select already installed approved capabilities compatible with the current grants. Unknown installations, network grants and executable upgrades require an explicit later host workflow. Catalog descriptions are untrusted. Trusted review badges are drawn by the host, not by the plugin itself.

## Runtime boundary

Reviewed first-party code may run as part of the application. That does not establish isolation for third-party code. MCP Apps provide a defined iframe/RPC boundary, but host configuration and remote server execution still require separate security work. An iframe has no portable hard CPU quota; resource-heavy/untrusted compute requires a separately reviewed strategy. Do not promise arbitrary generated code is safe because a manifest exists.

## Durable state

Persist attempts/notes separately from tool output. Store exact implementation version, inputs and meaningful state. No histories or embeddings per animation frame. Restore from recorded state, not from repeating remote side effects. Expired/missing plugins render a fallback and retain data. A generic MCP App without Desk state/semantic capabilities may be usable as an external tool but is not a fully integrated learning artifact.
